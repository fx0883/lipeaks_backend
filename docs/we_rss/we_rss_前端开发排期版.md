# we_rss 前端开发排期版

这份文档面向前端负责人和排期协同者，目标不是再次解释接口细节，而是把当前
`we_rss` 的真实能力拆成可执行的开发阶段、依赖关系和验收口径。

这次排期说明已经按最新数据结构重写。特别要注意的是，`we_rss` 全部核心模型
都已经继承 `BaseModel`，因此页面设计和状态管理要从一开始就考虑 tenant 共享、
软删除和“模型字段不等于接口字段”这三件事。

## 本期目标

这期前端工作的最低目标不是还原旧项目所有页面，而是跑通下面这条主链路：

1. 成员带 `Member JWT` 和 `X-Tenant-ID` 正常请求 `we_rss`。
2. 完成扫码登录，拿到有效微信凭证。
3. 设置默认凭证。
4. 搜索并保存公众号。
5. 触发公众号同步并轮询任务。
6. 在文章列表中看到同步下来的文章。
7. 支持文章详情、已读、收藏、刷新。
8. 需要时读取 RSS XML 和正文 HTML。

只要这条主链路完成，本期前端就已经可交付。

## 排期前必须统一的共识

排期前建议先统一下面几条团队共识：

- `we_rss` 数据是 tenant 共享，不是 member 私有。
- `DELETE` 接口是软删除。
- 公众号列表当前没有服务端分页和过滤。
- 文章列表支持 `article_type` 过滤，但还没有服务端分页、搜索和其它过滤。
- RSS / HTML 接口不是公开匿名地址。
- `result_payload` 是动态结构，不能先写死全局单一类型。

## 阶段拆分

### P0：基础联调阶段

这一阶段的目标是让前端具备和后端“稳定说话”的能力，并把最基础的扫码登录链路
跑通。`P0` 没完成前，不建议多人并行开发后面的复杂页面。

#### P0-1 统一请求层

目标：

- 封装 `weRssRequest`
- 封装 `weRssTextRequest`
- 统一注入 `Authorization`
- 统一注入 `X-Tenant-ID`
- 统一处理 JSON / XML / HTML 三种读取方式

依赖接口：

- 全部 `we_rss` 接口

验收标准：

- 能正常请求 `GET /credentials/`
- 漏传 `X-Tenant-ID` 时能稳定识别为联调问题
- RSS / HTML 接口不会被错误地按 JSON 解析

#### P0-2 通用任务轮询模块

目标：

- 统一封装任务轮询逻辑
- 支持 `pending / running / success / failed`
- 统一超时处理
- 统一失败提示

依赖接口：

- `GET /api/v1/we-rss/tasks/`
- `GET /api/v1/we-rss/tasks/{task_id}/`

验收标准：

- 扫码登录、公众号同步、文章导入、文章刷新都能复用同一套轮询逻辑

#### P0-3 凭证与扫码登录页

目标：

- 展示凭证列表
- 创建扫码登录会话
- 展示二维码
- 轮询登录结果
- 设置默认凭证
- 检查凭证状态

依赖接口：

- `GET /credentials/`
- `POST /credentials/login-sessions/`
- `GET /credentials/login-sessions/{session_id}/`
- `POST /credentials/{id}/set-default/`
- `POST /credentials/{id}/check/`
- `PUT /credentials/{id}/`
- `DELETE /credentials/{id}/`

验收标准：

- 能成功扫码并生成凭证
- 新凭证能出现在列表中
- 默认凭证可以切换
- 凭证状态检查结果可见

### P1：核心业务阶段

这一阶段的目标是跑通公众号和文章主链路。`P1` 完成后，这套前端就已经不是
“能联调”，而是“能真实使用”。

#### P1-1 公众号搜索与创建页

目标：

- 搜索微信平台公众号
- 从搜索结果保存为本地公众号
- 支持手动补充字段

依赖接口：

- `GET /feeds/search/?keyword=...`
- `POST /feeds/`

关键提醒：

- 搜索依赖有效凭证
- 搜索的是微信平台，不是本地库
- `credential_id` 传错 tenant 不会报错，但会绑定失败

验收标准：

- 有默认有效凭证时可以搜到公众号
- 可以将搜索结果保存为本地 feed

#### P1-2 公众号管理页

目标：

- 展示当前 tenant 的公众号列表
- 编辑公众号信息
- 删除公众号
- 触发公众号同步

依赖接口：

- `GET /feeds/`
- `GET /feeds/{id}/`
- `PUT /feeds/{id}/`
- `DELETE /feeds/{id}/`
- `POST /feeds/{id}/sync/`
- `GET /tasks/{task_id}/`

验收标准：

- 列表正常展示
- 可以修改 `mp_name`、`mp_intro`、`credential_id`、`is_featured`
- 能发起同步并看到任务结果

#### P1-3 文章导入入口

目标：

- 支持输入微信文章 URL 导入单篇文章
- 导入成功后能跳转文章详情或文章列表高亮

依赖接口：

- `POST /articles/import-by-url/`
- `GET /tasks/{task_id}/`

关键提醒：

- 导入是异步任务
- 相同 URL 导入任务会去重
- 后端会自动创建或复用精选 feed

验收标准：

- 输入合法微信文章 URL 后能生成导入任务
- 成功后能定位到导入结果文章

#### P1-4 文章列表页

目标：

- 展示文章列表
- 本地关键字过滤
- 本地按公众号过滤
- 本地按收藏过滤
- 更新已读状态
- 更新收藏状态
- 单篇刷新
- 删除文章

依赖接口：

- `GET /articles/`
- `GET /feeds/`
- `PUT /articles/{id}/read/`
- `PUT /articles/{id}/favorite/`
- `POST /articles/{id}/refresh/`
- `DELETE /articles/{id}/`
- `GET /tasks/{task_id}/`

关键提醒：

- 当前文章列表支持 `article_type` 服务端过滤
- 除 `article_type` 外，当前还没有服务端分页、搜索、按公众号、仅收藏过滤
- 页面其余筛选先做本地处理
- 删除是软删除
- 刷新文章走任务，不是同步立即完成

验收标准：

- 同步后的文章能在列表中看到
- 已读 / 收藏可正常切换
- 刷新成功后列表能看到最新字段

#### P1-5 文章详情页

目标：

- 展示标题、摘要、发布时间、正文
- 支持跳原文
- 支持从列表页进入详情

依赖接口：

- `GET /articles/{id}/`

可选增强接口：

- `GET /rss/content/{article_id}/`

验收标准：

- 能稳定展示正文 HTML
- 不依赖旧前端“上一篇 / 下一篇”接口

### P2：体验和补强阶段

这一阶段不是主链路阻塞项，但能提升交付完整度。

#### P2-1 RSS / HTML 调试页

目标：

- 查看 tenant RSS XML
- 查看单 feed RSS XML
- 查看单篇正文 HTML

依赖接口：

- `GET /rss/`
- `GET /rss/{feed_id}/`
- `GET /rss/content/{article_id}/`

验收标准：

- 三类文本都能正常读取与展示
- 页面能明确提醒这些接口仍然需要鉴权

#### P2-2 统一异常态与空态

目标：

- 统一 401 / 403 / 404 / 500 提示
- 统一任务失败提示
- 统一无凭证、无公众号、无文章时的空状态

依赖：

- 基于前面全部页面能力

验收标准：

- 从登录到文章阅读全链路没有明显断点

## 当前不要纳入本期排期的能力

这一节很重要。下面这些能力当前后端还没有提供，前端这期不要误以为已经可以做。

- 文章服务端分页
- 文章服务端搜索
- 文章服务端按公众号过滤
- 文章服务端仅收藏过滤
- 文章服务端仅未读过滤
- 上一篇 / 下一篇文章接口
- 公众号导入 / 导出
- OPML 导出
- Atom / JSON / Markdown / Text 等多格式输出
- 通过文章链接先识别公众号再引导订阅的专用接口

如果页面上暂时需要这些体验，建议：

- 先做本地过滤
- 先留 UI 占位
- 明确标注为后续需求，不要伪造接口

## 人力拆分建议

### 方案 A：3 人并行

前端 A 负责：

- 统一请求层
- 通用任务轮询
- 凭证与扫码登录页

前端 B 负责：

- 公众号搜索与创建页
- 公众号管理页

前端 C 负责：

- 文章列表页
- 文章详情页
- RSS / HTML 调试页

### 方案 B：2 人并行

前端 A 负责：

- P0 全部
- 公众号相关页面

前端 B 负责：

- 文章列表页
- 文章详情页
- RSS / HTML 页
- P2 收口

## 时间建议

如果前端框架基础设施已具备，且接口环境稳定，可以按下面节奏预估：

| 阶段 | 建议时长 | 说明 |
| --- | --- | --- |
| `P0` | 1 到 2 天 | 请求层、扫码登录、任务轮询 |
| `P1` | 2 到 4 天 | 公众号与文章主链路 |
| `P2` | 1 到 2 天 | RSS 调试、异常态、交互收口 |

如果只有 1 名开发，建议优先级如下：

1. P0 全部
2. 公众号搜索与同步
3. 文章列表
4. 文章详情
5. RSS / HTML 调试页

## 最终验收口径

这期前端收口时，建议按下面顺序验收：

1. 请求层能自动带鉴权头和 tenant 头。
2. 扫码登录能生成凭证。
3. 默认凭证设置生效。
4. 公众号搜索、保存、同步可用。
5. 同步后文章列表有数据。
6. 文章已读、收藏、刷新、删除都可用。
7. 文章详情可正常阅读。
8. RSS XML 和正文 HTML 可以读取。

只要这 8 条全部通过，就可以视为本期交付完成。
