# we_rss 前端开发排期版

这份文档把当前 `we_rss` 前端工作拆成 `P0 / P1 / P2` 三个阶段，适合前端
负责人排期、拆人、跟进联调进度时使用。

你可以把它理解成“开发优先级 + 依赖关系 + 人力拆分建议”。如果前端同学已
经拿到了接口说明和联调清单，这份文档就是进一步的执行版。

配套文档如下：

- [we_rss_前端完整API文档.md](./we_rss_%E5%89%8D%E7%AB%AF%E5%AE%8C%E6%95%B4API%E6%96%87%E6%A1%A3.md)
- [we_rss_前端联调清单版.md](./we_rss_%E5%89%8D%E7%AB%AF%E8%81%94%E8%B0%83%E6%B8%85%E5%8D%95%E7%89%88.md)

## 目标定义

这次前端开发的最低目标不是把旧项目 UI 全量搬过来，而是让新项目前端能把
下面这条业务链跑通：

1. 成员带 `Member JWT` 和 `X-Tenant-ID` 调用 `we_rss`
2. 完成扫码登录，拿到微信凭证
3. 搜索并保存公众号
4. 同步公众号文章
5. 浏览文章、标记已读、标记收藏、刷新文章
6. 读取 RSS XML 和文章正文 HTML

只要这条链跑通，本期前端目标就算完成。

## 阶段总览

建议排成三个阶段。

| 阶段 | 目标 | 是否阻塞后续 |
| --- | --- | --- |
| `P0` | 跑通基础请求层、凭证登录、任务轮询 | 是 |
| `P1` | 跑通公众号管理和文章主链路 | 是 |
| `P2` | 补 RSS 页、阅读体验和非核心增强 | 否 |

## P0：基础可联调阶段

`P0` 的核心目标是让前端具备和后端说话的能力，并把微信扫码登录这条基础链
路跑通。这个阶段一旦完成，团队就能开始并行做公众号和文章页面。

### P0 任务包

#### 任务 1：统一请求层

目标：

- 封装 `weRssRequest`
- 封装 `weRssTextRequest`
- 统一注入 `Authorization`
- 统一注入 `X-Tenant-ID`
- 统一解析标准 JSON 包裹

依赖接口：

- 全部 `we_rss` JSON 接口
- `GET /api/v1/we-rss/rss/`
- `GET /api/v1/we-rss/rss/{feed_id}/`
- `GET /api/v1/we-rss/rss/content/{article_id}/`

完成标准：

- 可以成功请求 `GET /credentials/`
- 漏传 tenant 头时能正常提示
- XML / HTML 不会被按 JSON 解析

#### 任务 2：统一任务轮询模块

目标：

- 封装通用轮询器
- 支持 `pending / running / success / failed`
- 统一错误提示
- 页面端只关心业务结果，不各自维护计时器

依赖接口：

- `GET /api/v1/we-rss/tasks/`
- `GET /api/v1/we-rss/tasks/{task_id}/`

完成标准：

- 登录、同步、导入、刷新都能复用同一套轮询逻辑

#### 任务 3：微信凭证与扫码登录页

目标：

- 展示凭证列表
- 支持创建扫码登录会话
- 支持展示二维码
- 支持轮询登录结果
- 支持设为默认凭证
- 支持检查凭证状态

依赖接口：

- `GET /api/v1/we-rss/credentials/`
- `POST /api/v1/we-rss/credentials/login-sessions/`
- `GET /api/v1/we-rss/credentials/login-sessions/{session_id}/`
- `POST /api/v1/we-rss/credentials/{id}/set-default/`
- `POST /api/v1/we-rss/credentials/{id}/check/`

完成标准：

- 能成功扫码
- 成功后凭证列表刷新
- 默认凭证可切换
- 凭证失效时能看到状态反馈

### P0 验收口径

`P0` 完成后，前端应该已经能在一个页面上证明：

- 请求层没问题
- tenant 头传递没问题
- 扫码登录没问题
- 任务轮询没问题

如果 `P0` 没完成，不建议前端大规模并行做后续页面。

## P1：主业务链路阶段

`P1` 是最核心的业务阶段。完成后，前端已经可以真正使用 `we_rss` 的主功
能，不再只是基础联调。

### P1 任务包

#### 任务 4：新增公众号 / 导入文章页

目标：

- 支持搜索公众号
- 支持从搜索结果创建公众号
- 支持输入微信文章 URL 导入单篇文章
- 导入成功后跳文章详情或文章列表

依赖接口：

- `GET /api/v1/we-rss/feeds/search/?keyword=...`
- `POST /api/v1/we-rss/feeds/`
- `POST /api/v1/we-rss/articles/import-by-url/`
- `GET /api/v1/we-rss/tasks/{task_id}/`

完成标准：

- 有默认凭证时，能搜到公众号
- 能保存公众号
- 能导入单篇文章

#### 任务 5：公众号管理页

目标：

- 展示当前 tenant 的公众号列表
- 支持编辑公众号
- 支持删除公众号
- 支持触发同步

依赖接口：

- `GET /api/v1/we-rss/feeds/`
- `GET /api/v1/we-rss/feeds/{id}/`
- `PUT /api/v1/we-rss/feeds/{id}/`
- `DELETE /api/v1/we-rss/feeds/{id}/`
- `POST /api/v1/we-rss/feeds/{id}/sync/`
- `GET /api/v1/we-rss/tasks/{task_id}/`

完成标准：

- 可以管理公众号基础信息
- 可以触发同步
- 同步结果可见

#### 任务 6：文章列表页

目标：

- 展示文章列表
- 提供本地关键词过滤
- 提供本地按公众号过滤
- 提供本地仅收藏过滤
- 支持已读 / 收藏切换
- 支持单篇刷新
- 支持删除

依赖接口：

- `GET /api/v1/we-rss/articles/`
- `GET /api/v1/we-rss/feeds/`
- `PUT /api/v1/we-rss/articles/{id}/read/`
- `PUT /api/v1/we-rss/articles/{id}/favorite/`
- `POST /api/v1/we-rss/articles/{id}/refresh/`
- `DELETE /api/v1/we-rss/articles/{id}/`
- `GET /api/v1/we-rss/tasks/{task_id}/`

特别说明：

当前后端还没有文章列表服务端筛选能力，所以本期前端先做本地筛选。

完成标准：

- 同步成功后的文章能显示出来
- 已读 / 收藏 / 刷新 / 删除都能正常工作

#### 任务 7：文章详情阅读页

目标：

- 展示文章标题、摘要、正文
- 支持跳原文
- 支持直接从文章列表进入

依赖接口：

- `GET /api/v1/we-rss/articles/{id}/`

可选增强接口：

- `GET /api/v1/we-rss/rss/content/{article_id}/`

完成标准：

- 能正常展示正文 HTML
- 页面不依赖旧项目的上一篇 / 下一篇接口

### P1 验收口径

`P1` 完成后，前端应该已经可以完整跑通：

1. 扫码登录
2. 搜索公众号
3. 创建公众号
4. 同步公众号
5. 浏览文章
6. 管理文章

这意味着新前端已经具备“能用”的版本。

## P2：增强与补全阶段

`P2` 不是主链路阻塞项，但它能显著提升交付完整度，适合在 `P1` 稳定后再
补。

### P2 任务包

#### 任务 8：RSS 调试页 / 输出页

目标：

- 展示 tenant RSS XML
- 展示单公众号 RSS XML
- 展示文章 HTML 输出

依赖接口：

- `GET /api/v1/we-rss/rss/`
- `GET /api/v1/we-rss/rss/{feed_id}/`
- `GET /api/v1/we-rss/rss/content/{article_id}/`

完成标准：

- 能正确获取 XML / HTML 文本
- 页面明确提示这类接口仍然需要鉴权

#### 任务 9：阅读体验增强

目标：

- 优化正文样式
- 加载中、空状态、失败状态统一
- 收藏和已读状态更直观
- 文章刷新时的按钮禁用和 loading 态

依赖：

- 无新增后端依赖

完成标准：

- 文章页和详情页体验达到可交付水平

#### 任务 10：联调收口与异常处理

目标：

- 统一 401 / 403 / 404 / 500 提示
- 统一任务失败提示
- 统一 tenant 错误提示
- 补页面间跳转回流

依赖：

- 基于前面所有页面能力

完成标准：

- 前端从登录到文章阅读全链路没有明显断点

## 推荐人力拆分

如果你有 3 个前端，建议这样拆。

### 方案 A：3 人并行

#### 前端 A

负责：

- 统一请求层
- 任务轮询模块
- 微信凭证与扫码登录页

优点：

- 把最底层能力集中在一个人手里
- 其他人可以稳定复用

#### 前端 B

负责：

- 新增公众号 / 导入文章页
- 公众号管理页

优点：

- 公众号相关能力集中
- 业务上下文连续

#### 前端 C

负责：

- 文章列表页
- 文章详情页
- RSS 调试页

优点：

- 文章阅读体验由一个人统一收口

### 方案 B：2 人并行

#### 前端 A

负责：

- P0 全部
- 公众号相关页面

#### 前端 B

负责：

- 文章列表页
- 文章详情页
- RSS 页
- P2 收口

## 推荐时间排法

如果接口稳定、前端框架已搭好，可以按下面节奏估算。

| 阶段 | 建议时长 | 说明 |
| --- | --- | --- |
| `P0` | `1` 到 `2` 天 | 主要是请求层、扫码、任务轮询 |
| `P1` | `2` 到 `4` 天 | 公众号和文章主链路 |
| `P2` | `1` 到 `2` 天 | RSS、体验、异常收口 |

如果只有 1 个前端，建议先只做：

1. `P0`
2. `P1` 里的新增公众号页
3. `P1` 里的文章列表页
4. `P1` 里的文章详情页

公众号管理页和 RSS 页可以后补。

## 当前不要排进去的能力

这部分很重要。下面这些旧前端里出现过的能力，当前 `we_rss` 后端还没有，
排期时先不要纳入本期目标。

- 文章服务端分页
- 文章服务端搜索
- 文章服务端按公众号过滤
- 仅收藏服务端过滤
- 上一篇 / 下一篇文章
- 公众号导入 / 导出
- OPML 导出
- Atom / JSON / Markdown / Text 多格式 RSS
- 通过文章链接识别公众号信息的专用接口

这些能力如果写进本期排期，会导致前端误以为接口已经准备好了。

## 最终验收建议

前端负责人在收口时，建议按下面顺序验收。

1. 验证统一请求层是否正确带 token 和 tenant 头
2. 验证扫码登录是否能成功生成凭证
3. 验证默认凭证是否生效
4. 验证公众号搜索、创建、同步
5. 验证文章列表加载
6. 验证文章已读、收藏、刷新、删除
7. 验证文章详情正文展示
8. 验证 RSS 和 HTML 输出

只要这 8 步都通过，这期前端交付就已经是完整可用版本。
