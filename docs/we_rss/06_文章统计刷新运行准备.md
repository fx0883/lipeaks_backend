# we_rss 文章统计刷新运行准备

这份文档面向前端、联调、测试和日常操作同学，说明调用下面 3 个刷新接口前，
你需要先准备什么环境，以及遇到问题时怎么排查。

这 3 个接口虽然都叫“刷新”，但依赖完全不同。`POST /api/v1/we-rss/articles/{id}/refresh/`
是正文刷新，走 `we_rss` 自己的文章抓取能力。`POST
/api/v1/we-rss/article-stats/refresh-by-url/` 和 `POST
/api/v1/we-rss/article-stats/refresh/` 是统计刷新，依赖
`scripts/lipeaks_viral_articles` 里的本地代理、证书和运行时文件。

## 先看结论

如果你只想先知道怎么操作，先记住下面这几点：

- 调正文刷新接口时，不需要开代理，不需要装证书。
- 调两个统计刷新接口前，必须先准备好本机代理环境。
- 统计刷新当前依赖这两个本地文件：
  `D:\GitHub\lipeaks_backend\scripts\lipeaks_viral_articles\output\wechat-stats\session.json`
  和
  `D:\GitHub\lipeaks_backend\scripts\lipeaks_viral_articles\output\wechat-stats\proxy-live.log`。
- 这两个文件不是接口自己生成的，你必须先启动代理，再用微信内置浏览器打开文章，
  让代理抓到请求。
- 单篇统计刷新按 URL 调用时，只会刷新已经存在于当前 tenant 里的文章。接口不会新建文章。
- 批量统计刷新是异步接口，只返回 `article_stats_refresh` 任务，不返回文章数据。

## 这 3 个接口分别依赖什么

调用前先区分“正文刷新”和“统计刷新”，否则很容易把准备工作做错。

| 接口 | 用途 | 是否同步 | 是否需要代理和证书 | 其他前置条件 |
| --- | --- | --- | --- | --- |
| `POST /api/v1/we-rss/articles/{id}/refresh/` | 刷新正文、摘要、封面、发布时间等内容 | 异步 | 否 | 需要 `we_rss` 默认微信凭证可用 |
| `POST /api/v1/we-rss/article-stats/refresh-by-url/` | 按 URL 同步刷新单篇文章统计，并返回整篇文章 | 同步 | 是 | URL 必须能匹配到当前 tenant 已存在文章 |
| `POST /api/v1/we-rss/article-stats/refresh/` | 批量异步刷新文章统计 | 异步 | 是 | 只能传一种选择器：`article_ids`、`feed_id`、`member_id` |

## 为什么统计刷新需要代理和证书

统计刷新不是直接用公开页面 HTML 就能拿到数据。当前实现会复用 POC
项目里已经验证过的方式，从微信文章相关请求里回放统计参数，再落回
`we_rss` 的文章表。

所以你在调用两个统计接口之前，必须先让本机准备好这套运行时：

- 本地 `mitmproxy` 代理正在运行。
- Windows 手动代理已经指向 `127.0.0.1:8082`。
- `mitmproxy` 根证书已经安装到系统信任区。
- 微信内置浏览器访问过文章，已经产生了最新的 `session.json` 和
  `proxy-live.log`。

如果这两个运行时文件不存在，后端会直接报错：

```text
WeChat article stats runtime is not ready. Missing: session.json, proxy-live.log.
```

## 运行时文件放在哪里

当前 `we_rss` 代码会固定读取下面这个目录，所以联调机器上的路径必须存在。
更准确地说，必须是在运行 `we_rss` 服务的那台机器上存在，因为接口读取的是后端
本机文件，不是前端浏览器本地文件。

```text
D:\GitHub\lipeaks_backend\scripts\lipeaks_viral_articles\output\wechat-stats
```

目录里最关键的是下面两个文件：

- `session.json`
- `proxy-live.log`

你还可能看到这些文件：

- `latest.json`：代理调试快照，不是接口硬性依赖。
- `<短链ID>.json`：POC 单独跑脚本时生成的结果文件，接口本身不依赖这个文件。

## 安装 mitmproxy

统计刷新依赖 `mitmdump`。如果机器上还没装，先安装它。

1. 打开 PowerShell。
2. 确认本机 Python 可用。
3. 执行下面的安装命令：

```powershell
python -m pip install mitmproxy
```

安装后，建议立刻验证：

```powershell
mitmdump --version
```

如果你的环境变量还没生效，也可以这样验证：

```powershell
python -m mitmproxy --version
```

> **Note:** 当前仓库里的代理启动脚本默认写死了
> `C:\Users\Administrator\AppData\Local\Programs\Python\Python313\Scripts\mitmdump.exe`。
> 如果你的 `mitmdump.exe` 不在这个位置，需要先调整
> `scripts\run-wechat-stats-proxy.ps1` 里的路径，或者在同样位置准备好可执行文件。

## 启动本地代理

代理脚本依赖相对路径加载 addon，所以你最好从
`scripts/lipeaks_viral_articles` 项目根目录启动它。

1. 打开 PowerShell。
2. 进入下面这个目录：

```powershell
cd D:\GitHub\lipeaks_backend\scripts\lipeaks_viral_articles
```

3. 启动代理：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\run-wechat-stats-proxy.ps1
```

当前脚本默认监听下面这个地址：

- 主机：`127.0.0.1`
- 端口：`8082`

如果代理已经成功启动，你可以再开一个 PowerShell 窗口验证：

```powershell
Get-Process mitmdump
```

## 配置 Windows 手动代理

代理进程启动后，还需要把系统代理指到本机端口。否则微信流量不会经过
`mitmproxy`，`session.json` 和 `proxy-live.log` 也不会更新。

1. 保持 `run-wechat-stats-proxy.ps1` 正在运行。
2. 打开 Windows **设置**。
3. 进入 **网络和 Internet**。
4. 打开 **代理**。
5. 在 **手动设置代理服务器** 中启用代理。
6. 地址填写 `127.0.0.1`。
7. 端口填写 `8082`。
8. 保存设置。

如果你不再做统计刷新联调，记得在联调结束后把系统代理关掉，避免影响其他应用。

## 安装 mitmproxy 根证书

第一次在这台机器上抓微信 HTTPS 流量时，你还需要安装证书。没有这一步，
代理虽然能跑起来，但微信请求通常不能被正常解密。

1. 保持本地代理运行。
2. 用浏览器打开 `http://mitm.it`。
3. 下载当前系统对应的证书。
4. 双击证书文件，开始安装。
5. 选择 **当前用户** 或 **本地计算机**。
6. 选择 **将所有的证书放入下列存储**。
7. 选择 **受信任的根证书颁发机构**。
8. 完成导入。
9. 重启微信客户端。

> **Warning:** 证书必须导入到 **受信任的根证书颁发机构**。如果导入到了别的证书库，
> 代理通常仍然抓不到可用的微信 HTTPS 内容。

## 刷新 session.json 和 proxy-live.log

统计接口真正依赖的不是“代理进程已启动”，而是“代理已经抓到了最新会话数据”。
所以装完代理和证书后，还要再做一次会话刷新。

1. 保持代理运行，Windows 代理保持开启。
2. 打开微信客户端。
3. 用微信内置浏览器打开任意一篇目标公众号文章。
4. 在文章页停留几秒，等请求经过代理。
5. 回到 PowerShell 检查输出目录文件是否更新。

建议用下面两个命令确认：

```powershell
Get-Content D:\GitHub\lipeaks_backend\scripts\lipeaks_viral_articles\output\wechat-stats\proxy-live.log -Tail 30
```

```powershell
Get-Item D:\GitHub\lipeaks_backend\scripts\lipeaks_viral_articles\output\wechat-stats\session.json | Select-Object LastWriteTime
```

如果 `proxy-live.log` 里能看到文章相关请求，且 `session.json` 的修改时间刚刚更新，
就说明统计运行时已经准备好了。

## 调接口前怎么确认环境已经准备好

真正发起统计刷新前，建议按下面顺序做一次快速自检。

1. 确认 `mitmdump` 进程存在。
2. 确认 Windows 手动代理仍然指向 `127.0.0.1:8082`。
3. 确认证书已经导入，微信已重启。
4. 确认 `session.json` 存在。
5. 确认 `proxy-live.log` 存在。
6. 确认这两个文件的更新时间是最近一次操作之后。
7. 如果调用的是 `refresh-by-url`，确认 URL 对应的文章已经在当前 tenant 里存在。
8. 如果调用的是批量刷新，确认你只传了一个选择器。

## 三个接口各自怎么调

下面给的是联调时最实用的调用方式。所有接口都需要正常登录后的
`Authorization`，以及当前租户头 `X-Tenant-ID`。

### 1. 正文刷新接口

正文刷新不依赖 POC 代理环境。它和统计刷新是两套链路。

调用前你只需要确认：

- 当前用户已经登录。
- 当前 tenant 下已经设置可用的默认微信凭证。
- 目标文章 `id` 已存在。

示例：

```http
POST /api/v1/we-rss/articles/123/refresh/
Authorization: Bearer <token>
X-Tenant-ID: <tenant_id>
```

这个接口会返回异步任务对象。前端拿到 `data.id` 后，继续轮询任务接口即可。

### 2. 单篇统计同步刷新接口

单篇统计刷新会先更新数据库，再直接返回更新后的整篇文章数据。

调用前你需要确认：

- 代理环境已经准备好。
- `session.json` 和 `proxy-live.log` 已经更新。
- 文章 URL 对应的记录已经存在于当前 tenant。

示例：

```http
POST /api/v1/we-rss/article-stats/refresh-by-url/
Authorization: Bearer <token>
X-Tenant-ID: <tenant_id>
Content-Type: application/json

{
  "url": "https://mp.weixin.qq.com/s/xxxxxxxxxxxx"
}
```

接口特征：

- 同步返回，不需要轮询任务。
- 返回的是更新后的整篇 `WechatArticle`。
- 如果这个 URL 在当前 tenant 下匹配不到文章，会直接返回 `404 Article not found.`。

### 3. 批量统计异步刷新接口

批量统计刷新会创建异步任务。底层会先解析出要刷新的文章集合，再逐篇刷新统计。

你只能传下面三种选择器中的一种：

- `article_ids`
- `feed_id`
- `member_id`

示例一，刷新选中的文章：

```http
POST /api/v1/we-rss/article-stats/refresh/
Authorization: Bearer <token>
X-Tenant-ID: <tenant_id>
Content-Type: application/json

{
  "article_ids": [101, 102, 103]
}
```

示例二，刷新某个公众号下全部文章：

```http
POST /api/v1/we-rss/article-stats/refresh/
Authorization: Bearer <token>
X-Tenant-ID: <tenant_id>
Content-Type: application/json

{
  "feed_id": 5
}
```

示例三，刷新某个成员订阅范围下全部文章：

```http
POST /api/v1/we-rss/article-stats/refresh/
Authorization: Bearer <token>
X-Tenant-ID: <tenant_id>
Content-Type: application/json

{
  "member_id": 9
}
```

接口特征：

- 异步返回，不直接返回文章数组。
- 成功创建后返回的是 `article_stats_refresh` 任务对象。
- 如果同时传了多个选择器，会直接报错：
  `Provide exactly one of article_ids, feed_id, or member_id.`

## 推荐操作顺序

如果你准备联调两个统计刷新接口，推荐按下面顺序走，成功率最高。

1. 安装 `mitmproxy`。
2. 从 `scripts/lipeaks_viral_articles` 目录启动代理。
3. 在 Windows 里开启手动代理，指向 `127.0.0.1:8082`。
4. 安装 `mitmproxy` 根证书。
5. 重启微信。
6. 用微信内置浏览器打开一篇文章，刷新 `session.json` 和 `proxy-live.log`。
7. 先调一次 `POST /api/v1/we-rss/article-stats/refresh-by-url/` 验证单篇同步刷新。
8. 再调 `POST /api/v1/we-rss/article-stats/refresh/` 验证批量异步刷新。

## 常见问题

这里列的是联调时最常见的几类问题，基本都能直接对上现象。

### 接口提示缺少 session.json 或 proxy-live.log

这说明后端读取运行时目录时，没有看到必需文件。先排查下面几项：

1. 代理是否真的启动了。
2. Windows 代理是否真的指向了 `127.0.0.1:8082`。
3. 微信文章是否真的通过微信内置浏览器打开过。
4. 输出目录是否就是
   `D:\GitHub\lipeaks_backend\scripts\lipeaks_viral_articles\output\wechat-stats`。

### 代理开着，但文件一直不更新

这通常是系统代理没生效，或者证书没装对。先检查：

1. `Get-Process mitmdump` 是否还能看到进程。
2. `proxy-live.log` 是否持续有新内容。
3. 证书是否导入到了 **受信任的根证书颁发机构**。
4. 微信是否在装完证书后重启过。

### 单篇统计刷新返回 404

这不是代理问题，而是这条 URL 在当前 tenant 下没有对应文章记录。
当前实现不会根据 URL 自动创建新文章，只会刷新已存在文章的统计字段。

### 批量统计刷新没有返回文章数据

这是正常行为。`POST /api/v1/we-rss/article-stats/refresh/` 设计上只返回任务对象。
如果你要拿到文章详情，应该在任务完成后重新请求文章列表或文章详情接口。

### 我只是想刷新正文，为什么还要装代理

不需要。正文刷新走的是另外一套链路。只有两个统计刷新接口才依赖代理、
证书和 `session.json` / `proxy-live.log`。
