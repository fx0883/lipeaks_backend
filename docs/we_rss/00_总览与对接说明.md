# we_rss 总览与对接说明

这份文档先讲清楚 `we_rss` 的整体边界、鉴权方式、tenant 隔离、返回格式，
以及当前最重要的数据模型变化。你在具体接每个接口之前，建议先把这一页读
完，因为这次最大的变化不是接口路径，而是“哪些数据 tenant 共享，哪些状态
是 member 维度”。

`we_rss` 当前是一套面向微信公众号抓取与阅读的独立业务模块，包含微信凭证、
扫码登录、公众号搜索与同步、文章列表与详情、异步任务，以及需要鉴权的 RSS
和 HTML 输出。这里的文章模型是 `WechatArticle`，和项目中的 `cms.Article`
没有直接关系，前端不要混用。

## 基础地址

所有 `we_rss` 接口都挂在统一前缀下：

```text
/api/v1/we-rss/
```

本地开发环境通常是：

```text
http://localhost:8000/api/v1/we-rss/
```

## 鉴权与 tenant 要求

所有 `we_rss` 接口都要求使用成员身份访问，并且必须显式携带租户头。接口层
统一要求 `IsAuthenticated` 和 `IsTenantMemberForWeRss`，所以匿名请求、
管理员口径请求、缺少 tenant 的成员请求都不属于这套接口的正常使用方式。

标准请求头如下：

```http
Authorization: Bearer <member_access_token>
X-Tenant-ID: <current_member_tenant_id>
```

这里有几条必须遵守的规则：

- `Authorization` 必填。
- `X-Tenant-ID` 必填。
- `X-Tenant-ID` 必须等于当前登录 member 实际绑定的 `tenant.id`。
- member 如果没有绑定 tenant，会被直接拒绝访问。
- 不能跨 tenant 访问或写入任何 `we_rss` 数据。

## tenant 共享和 member 个性化状态

`we_rss` 的主数据隔离单位仍然是 tenant，不是 member。也就是说，一个成员在
当前 tenant 下登录得到的微信凭证，其他同 tenant 成员也能继续使用；公众号、
文章、同步任务、RSS 输出也都是 tenant 共享主数据。

但这次有两个状态已经改成 member 维度：

- member 自己订阅哪些公众号，通过 `MemberFeedSubscription` 维护。
- member 自己收藏哪些文章，通过 `MemberArticleFavorite` 维护。
- member 自己有哪些私有标签，以及这些标签和 feed/article 的绑定关系，
  通过 `MemberTag`、`MemberFeedTagRelation`、`MemberArticleTagRelation`
  维护。

这意味着前端需要分清楚两类数据：

- tenant 共享主数据：`WechatFeed`、`WechatArticle`、`WechatSyncTask`
- member 个性化状态：`is_subscribed`、`is_favorite`、member 私有标签

当前可以这样理解：

- 所有 member 默认都能看当前 tenant 的全部文章。
- 所有 member 默认都能看当前 tenant 的全部 feed 主数据。
- `is_subscribed` 只表示“当前 member 是否订阅了这条 feed”。
- `is_favorite` 只表示“当前 member 是否收藏了这篇文章”。
- 标签是当前 member 的私有资产，不存在 tenant 公共标签。
- 原有 `feeds/` 和 `articles/` 主响应结构保持不变，标签能力通过独立标签
  API 和对象标签 API 提供。
- 当前没有 member 维度的已读状态，接口里也没有 `is_read`。

## 标准返回格式

绝大多数业务接口返回 JSON 包装结构。前端实际消费的数据在 `data` 字段中。

```json
{
  "success": true,
  "code": 2000,
  "message": "操作成功",
  "data": {}
}
```

字段含义如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `success` | `boolean` | 是否成功 |
| `code` | `number` | 业务码，成功通常是 `2000` |
| `message` | `string` | 结果说明 |
| `data` | `object \| array \| null` | 真实业务数据 |

## 非 JSON 接口

`we_rss` 不全是 JSON 接口。RSS 和正文输出接口返回的是文本内容，前端要按
文本去读取。

| 接口类型 | Content-Type | 前端读取方式 |
| --- | --- | --- |
| 普通业务接口 | `application/json` | `await response.json()` |
| RSS 输出 | `application/xml` | `await response.text()` |
| 正文输出 | `text/html` | `await response.text()` |

> **注意：** RSS 和正文输出接口虽然不是 JSON，但仍然要求成员鉴权和
> `X-Tenant-ID`，它们不是公开匿名链接。

## 当前接口能力概览

当前已经开放的核心能力如下：

- 微信凭证管理
- 微信扫码登录
- 公众号搜索
- member 订阅公众号和取消订阅
- member 私有标签 CRUD
- feed 标签绑定、解绑、查询
- article 标签绑定、解绑、查询
- 公众号同步任务
- 文章列表、详情、标题搜索、收藏、按 URL 导入、刷新、删除
- 异步任务轮询
- tenant RSS、单 feed RSS、正文 HTML 输出

## member 私有标签

当前标签系统按 member 私有资产设计。每个 member 只能看到和操作自己的标
签，不存在 tenant 共享标签，也不考虑子账号兼容语义。

标签的业务规则如下：

- 同一个 member 下，标签名全局唯一，且大小写不敏感，例如 `AI` 和 `ai`
  视为同一个标签。
- 标签字段包括 `name`、`color`、`description`、`sort_order`、
  `is_pinned`。
- 标签列表默认按 `is_pinned desc, sort_order asc, id desc` 排序。
- 标签列表返回 `feed_count` 和 `article_count`，前端可以直接展示统计值。
- 标签既可以绑定到 feed，也可以绑定到 article，同一个标签可以同时用于两
  种对象。
- feed 打标签前，当前 member 必须先订阅该 feed。
- article 打标签只要求文章在当前 tenant 中存在，不要求当前 member 已订
  阅对应 feed。
- attach 和 detach 都是增量操作，请求体使用 `tag_ids` 数组，不会自动创建
  标签。
- feed 和 article 列表都支持 `tag_ids=1,2,3` 查询参数，多个标签使用 AND
  语义，并且只会匹配当前 member 自己的标签关系。
- 删除标签时会自动删除该标签在 feed/article 上的全部关系。
- 当前 member 取消订阅 feed 时，会自动清理该 member 在这个 feed 上的所
  有标签关系。

## 这次对前端最重要的变化

你在接入时要优先同步下面这些变化：

1. 文章不再有全局 `is_read` 和全局 `is_favorite`。
2. 文章列表新增 `search`，并且只搜 `title`。
3. 文章列表新增 `favorite_only=true`，表示只看当前 member 的收藏。
4. 公众号列表新增 `subscribed_only=true`，表示只看当前 member 已订阅的
   feed。
5. 新增独立标签 API，以及 `feeds/{id}/tags/*`、`articles/{id}/tags/*`
   对象标签 API。
6. feed 和 article 列表都支持 `tag_ids` 过滤，并且多个标签是 AND 语义。
7. 搜索公众号后，标准动作是 `POST /feeds/subscribe/`，不是直接调用
   `POST /feeds/`。
8. feed 和 article 仍然是 tenant 共享主数据，不要把它们设计成 member
   私有资源。

## 推荐前端请求封装

前端最好一开始就把 `we_rss` 的 JSON 请求和文本请求分成两个统一入口，这样
后续联调时不会在 RSS 或 HTML 接口上误用 `response.json()`。

```ts
type ApiEnvelope<T> = {
  success: boolean;
  code: number;
  message: string;
  data: T;
};

async function weRssRequest<T>(
  path: string,
  options: RequestInit = {},
): Promise<ApiEnvelope<T>> {
  const token = localStorage.getItem("member_access_token");
  const tenantId = localStorage.getItem("member_tenant_id");

  const response = await fetch(`/api/v1/we-rss${path}`, {
    ...options,
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${token}`,
      "X-Tenant-ID": String(tenantId),
      ...(options.headers || {}),
    },
  });

  return response.json();
}

async function weRssTextRequest(path: string): Promise<string> {
  const token = localStorage.getItem("member_access_token");
  const tenantId = localStorage.getItem("member_tenant_id");

  const response = await fetch(`/api/v1/we-rss${path}`, {
    headers: {
      Authorization: `Bearer ${token}`,
      "X-Tenant-ID": String(tenantId),
    },
  });

  return response.text();
}
```

## 推荐接入顺序

如果前端要从零开始接这套模块，建议按下面顺序推进：

1. 先接统一请求层，确保 token 和 `X-Tenant-ID` 自动注入。
2. 接扫码登录和凭证管理。
3. 接公众号搜索、订阅和同步。
4. 接任务轮询。
5. 接文章列表、标题搜索、收藏、详情和刷新。
6. 最后再接 RSS 和正文 HTML。
