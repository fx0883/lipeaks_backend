# we_rss 总览与对接说明

这份文档先讲清楚 `we_rss` 的整体边界、鉴权方式、租户隔离、返回格式和最新
数据结构变化。你在具体接每个接口之前，建议先把这一页读完，因为这次最大的
变化不是接口路径，而是“模型字段”和“接口字段”已经不能混为一谈。

`we_rss` 当前是一套面向微信公众号抓取与阅读的独立业务模块，包含下面几类
能力：微信凭证、扫码登录、公众号管理、公众号文章管理、异步同步任务，以及
需要鉴权的 RSS / HTML 输出。这里的文章模型是 `WechatArticle`，与项目中的
`cms.Article` 没有直接关系，前端不要混用。

关于文章链接还有一个需要统一认知的点：`WechatArticle.url` 保存的是归一化后的公开文章链接，
用于阅读、刷新、RSS 输出和任务去重。抓取过程中微信跳转地址里出现的 `token` 等临时参数不会入库。

## 基础地址

所有 `we_rss` 接口都挂在统一前缀下。

```text
/api/v1/we-rss/
```

本地开发环境通常会是：

```text
http://localhost:8000/api/v1/we-rss/
```

## 鉴权与租户要求

所有 `we_rss` 接口都要求使用成员身份访问，并且必须显式携带租户头。接口层
在 `we_rss/views/base.py` 中统一要求 `IsAuthenticated` 和
`IsTenantMemberForWeRss`，所以匿名请求、管理员口径请求、缺 tenant 的成员
请求都不属于这套接口的正常使用方式。

标准请求头如下：

```http
Authorization: Bearer <member_access_token>
X-Tenant-ID: <current_member_tenant_id>
```

这里有几个必须遵守的规则：

- `Authorization` 必填。
- `X-Tenant-ID` 必填。
- `X-Tenant-ID` 必须等于当前登录成员实际绑定的 `tenant.id`。
- 成员如果没有绑定 tenant，会被直接拒绝访问。
- 不能跨 tenant 访问或写入任何 `we_rss` 数据。

## tenant 共享，不是 member 私有

`we_rss` 的数据隔离单位是 tenant，不是 member。也就是说，一个成员在当前
tenant 下扫码登录生成的微信凭证，其他同 tenant 成员也能看到并继续使用。
公众号、文章、同步任务也是同样的逻辑。

前端在命名和 UI 文案上最好统一使用下面这种表达：

- 当前租户的微信凭证
- 当前租户的公众号
- 当前租户的文章
- 当前租户的同步任务

不建议写成“我的公众号”“我的文章”“我的微信凭证”，因为这会误导用户。

## 标准返回格式

绝大多数业务接口返回 JSON 包装结构。前端实际消费的数据在 `data` 字段中。

```json
{
  "success": true,
  "code": 2000,
  "message": "操作成功",
  "data": {}
}
```

字段含义如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `success` | `boolean` | 是否成功 |
| `code` | `number` | 业务码，成功通常为 `2000` |
| `message` | `string` | 结果说明 |
| `data` | `object \| array \| null` | 真实业务数据 |

## 非 JSON 接口

`we_rss` 不全是 JSON 接口。RSS 和正文输出接口返回的是文本内容，前端要按
文本去读取。

| 接口类型 | Content-Type | 前端读取方式 |
| --- | --- | --- |
| 普通业务接口 | `application/json` | `await response.json()` |
| RSS 输出 | `application/xml` | `await response.text()` |
| 正文输出 | `text/html` | `await response.text()` |

> **注意：** RSS 和正文输出接口虽然不是 JSON，但仍然需要带成员 token 和
> `X-Tenant-ID`，它们不是公开匿名链接。

## 当前数据结构变化

这次 `we_rss` 文档重写的核心原因，是 `we_rss/models.py` 中的五个模型都已经
统一继承了 `common.models.BaseModel`。这意味着它们现在在数据库层和模型层
都具备了一组公共字段和行为。

统一继承 `BaseModel` 的模型包括：

- `WechatCredential`
- `WechatCredentialLoginSession`
- `WechatFeed`
- `WechatArticle`
- `WechatSyncTask`

### BaseModel 统一提供了什么

`BaseModel` 当前统一提供：

| 字段或能力 | 说明 |
| --- | --- |
| `tenant` | 数据归属租户 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `is_deleted` | 软删除标记 |
| `objects` | 默认租户感知、且会过滤 `is_deleted = false` 的管理器 |
| `original_objects` | 不做默认过滤的原始管理器 |
| `soft_delete()` | 软删除方法 |

### 这对前端意味着什么

这次变化最重要的不是“接口多返回了哪些字段”，而是“模型层对齐了，但接口层
仍然只暴露 serializer 中定义的字段”。前端需要明确区分下面三类字段：

| 类型 | 含义 |
| --- | --- |
| 模型字段 | 数据库和 Django model 中真实存在的字段 |
| 接口返回字段 | serializer 暴露给前端的字段 |
| 接口可写字段 | create / update / action 请求体允许提交的字段 |

举个最直接的例子：

- `WechatCredential` 模型里现在有 `tenant`、`token`、`cookie`、
  `created_by`、`updated_by`、`is_deleted`。
- 但凭证详情接口返回给前端的字段只有 `id`、`name`、`status`、
  `expires_at`、`last_login_at`、`last_check_at`、`last_error`、
  `is_default`、`created_at`、`updated_at`。
- 更新凭证接口也不是全字段可写，而是只允许改 `name`。即便你传了 `token`
  或 `cookie`，当前代码也会主动报错。

## 软删除语义

由于所有业务模型都已经继承 `BaseModel`，并且 `TenantModelViewSet` 在删除时
优先调用 `soft_delete()`，所以 `we_rss` 下的 `DELETE` 接口现在都应该理解为
软删除，而不是物理删除。

这意味着：

- 删除成功后通常返回 `204 No Content`。
- 数据会被标记为 `is_deleted = true`。
- 默认查询结果中不会再出现这条数据。
- 如果业务后续真的需要“回收站”或“恢复”能力，要额外设计接口，目前没有。

## 异步任务模型

`we_rss` 中有不少动作不是同步直接返回最终结果，而是先创建任务，再由前端
轮询任务状态。

当前四类任务如下：

| `task_type` | 用途 |
| --- | --- |
| `credential_login` | 扫码登录后台轮询任务 |
| `feed_sync` | 公众号同步任务 |
| `article_import` | 文章按 URL 导入任务 |
| `article_refresh` | 单篇文章刷新任务 |

前端在接入时要统一理解两件事：

- 触发接口不一定返回最终业务结果，很多时候只返回 `WechatSyncTask`。
- `result_payload` 的结构会随着 `task_type` 不同而变化，不能假设它总是同一套
  JSON 结构。

## 推荐前端请求封装

前端最好一开始就把 `we_rss` 的 JSON 请求和文本请求分成两个统一入口。这样
后续联调时不会在 RSS / HTML 接口上误用 `response.json()`。

```ts
type ApiEnvelope<T> = {
  success: boolean;
  code: number;
  message: string;
  data: T;
};

async function weRssRequest<T>(
  path: string,
  options: RequestInit = {},
): Promise<ApiEnvelope<T>> {
  const token = localStorage.getItem("member_access_token");
  const tenantId = localStorage.getItem("member_tenant_id");

  const response = await fetch(`/api/v1/we-rss${path}`, {
    ...options,
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${token}`,
      "X-Tenant-ID": String(tenantId),
      ...(options.headers || {}),
    },
  });

  return response.json();
}

async function weRssTextRequest(path: string): Promise<string> {
  const token = localStorage.getItem("member_access_token");
  const tenantId = localStorage.getItem("member_tenant_id");

  const response = await fetch(`/api/v1/we-rss${path}`, {
    headers: {
      Authorization: `Bearer ${token}`,
      "X-Tenant-ID": String(tenantId),
    },
  });

  return response.text();
}
```

## 推荐接入顺序

如果前端要从零开始接这套模块，建议按下面顺序推进。

1. 先接统一请求层，确保 token 和 `X-Tenant-ID` 自动注入。
2. 接扫码登录和凭证管理。
3. 接公众号搜索、创建、编辑和同步。
4. 接任务轮询。
5. 接文章列表、详情、已读、收藏、刷新。
6. 最后再接 RSS 和正文 HTML。
