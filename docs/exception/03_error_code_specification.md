# 错误码规范

## 概述

本文档定义了 Lipeaks Backend 项目的错误码规范，确保所有API错误响应使用统一的错误码体系。

## 错误码结构

### 基本格式

错误码采用**4位数字**格式：`XYZZ`

```
4 1 0 1
│ │ │ └─ 具体错误序号 (01-99)
│ │ └─── 固定为0（预留）
│ └───── 业务模块标识 (0-9)
└─────── 错误类别 (4=客户端, 5=服务端)
```

### 错误类别

| 第1位 | 类别 | 说明 | 示例 |
|-------|------|------|------|
| 4 | 客户端错误 | 请求参数错误、权限不足等 | 4101, 4201 |
| 5 | 服务端错误 | 服务器内部错误、数据库错误等 | 5000, 5001 |

## 错误码使用规范

### 1. 选择合适的错误码

**原则：**
- 优先使用已定义的错误码
- 新错误码应符合模块范围
- 避免重复定义相同语义的错误码

**示例：**
```python
# ✅ 好的做法 - 使用已定义的错误码
class TenantNotFoundException(TenantException):
    business_code = 4101
    error_code = 'TENANT_NOT_FOUND'

# ❌ 不好的做法 - 创建重复的错误码
class TenantNotExistException(TenantException):
    business_code = 4199  # 应该使用4101
    error_code = 'TENANT_DOES_NOT_EXIST'  # 与TENANT_NOT_FOUND重复
```

### 2. 错误标识符命名规范

**格式：** `MODULE_DESCRIPTION`

**规则：**
- 全大写字母
- 使用下划线分隔单词
- 以模块名开头
- 描述具体明确

**示例：**
```python
# ✅ 好的命名
'TENANT_NOT_FOUND'
'LICENSE_EXPIRED'
'USER_PERMISSION_DENIED'
'POINTS_INSUFFICIENT'

# ❌ 不好的命名
'NotFound'  # 缺少模块前缀
'tenant_error'  # 应该全大写
'ERR_001'  # 不描述性
'LicenseIsExpiredError'  # 太冗长
```

### 3. 错误消息编写规范

**原则：**
- 简洁明了，说明问题
- 不暴露敏感信息
- 提供上下文信息（当适用时）
- 使用用户友好的语言

**示例：**
```python
# ✅ 好的错误消息
"租户ID 123 不存在"
"许可证已于 2024-01-15 过期"
"积分余额不足，当前可用: 100，需要: 500"

# ❌ 不好的错误消息
"Error in database query"  # 暴露技术细节
"失败"  # 信息不足
"Tenant with ID 123 was not found in table tenant_table where is_deleted=0"  # 暴露数据库结构
```

### 4. HTTP状态码映射

| 业务场景 | HTTP状态码 | 示例 |
|---------|-----------|------|
| 资源不存在 | 404 | 租户不存在、许可证不存在 |
| 权限不足 | 403 | 租户访问拒绝、用户权限不足 |
| 认证失败 | 401 | Token无效、未登录 |
| 请求参数错误 | 400 | 数据验证失败、业务规则不满足 |
| 配额超限 | 429 | 请求频率限制、配额超限 |
| 服务器错误 | 500 | 数据库错误、系统异常 |

## 错误响应格式

### 标准格式

```json
{
    "success": false,
    "code": 4101,
    "message": "租户ID 123 不存在",
    "data": null,
    "error_code": "TENANT_NOT_FOUND"
}
```

### 字段说明

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `success` | boolean | 是 | 请求是否成功，错误时固定为 `false` |
| `code` | integer | 是 | 业务错误码（4位数字） |
| `message` | string | 是 | 人类可读的错误消息 |
| `data` | any | 是 | 错误详情数据，通常为 `null`，验证错误时包含字段错误信息 |
| `error_code` | string | 是 | 错误标识符（字符串常量） |

### 验证错误特殊格式

当发生数据验证错误时，`data` 字段包含字段级错误信息：

```json
{
    "success": false,
    "code": 4000,
    "message": "数据验证失败",
    "data": {
        "name": ["该字段不能为空"],
        "email": ["请输入有效的邮箱地址"],
        "age": ["必须是正整数"]
    },
    "error_code": "VALIDATION_ERROR"
}
```

## 添加新错误码

### 流程

1. **确定模块** - 确认新错误属于哪个业务模块
2. **检查是否已存在** - 在错误码表中查找是否已有类似错误
3. **分配错误码** - 在模块范围内选择未使用的序号
4. **定义错误标识符** - 遵循命名规范创建标识符
5. **更新文档** - 在本文档中添加新错误码定义
6. **实现异常类** - 创建或更新对应的异常类
7. **代码评审** - 确保符合规范

### 示例

假设需要添加"许可证密钥格式无效"的错误：

**步骤1：确定模块**
- 模块：许可证管理（42XX）

**步骤2：检查是否已存在**
- 检查4200-4299范围，发现没有"密钥格式无效"的错误

**步骤3：分配错误码**
- 当前已使用：4201-4208
- 新错误码：4209

**步骤4：定义错误标识符**
- 标识符：`LICENSE_INVALID_KEY_FORMAT`

**步骤5：更新文档**
```markdown
| 4209 | `LICENSE_INVALID_KEY_FORMAT` | 400 | 许可证密钥格式无效 | "许可证密钥格式不正确" |
```

**步骤6：实现异常类**
```python
class LicenseInvalidKeyFormatException(LicenseException):
    status_code = 400
    business_code = 4209
    error_code = 'LICENSE_INVALID_KEY_FORMAT'
    default_detail = '许可证密钥格式不正确'
```

**步骤7：代码评审**
- 提交PR，团队评审

## 错误码管理

### 版本控制

- 错误码一旦发布不应修改
- 废弃的错误码应标记为deprecated
- 新版本可以添加新错误码

### 废弃错误码

标记为废弃但保留向后兼容：

```python
# ⚠️ Deprecated: Use TENANT_NOT_FOUND (4101) instead
TENANT_DOES_NOT_EXIST = 4150  # Will be removed in v2.0
```

### 错误码注册表

维护一个集中的错误码注册表文件：`common/exceptions/error_codes.py`

```python
# 错误码常量定义
class ErrorCodes:
    # 认证授权 (40XX)
    AUTH_NOT_AUTHENTICATED = 4001
    AUTH_PERMISSION_DENIED = 4003
    
    # 租户管理 (41XX)
    TENANT_NOT_FOUND = 4101
    TENANT_INACTIVE = 4102
    
    # 许可证管理 (42XX)
    LICENSE_EXPIRED = 4201
    LICENSE_NOT_FOUND = 4202
    
    # ... 更多错误码
```

## 总结

遵循本规范可以：

1. ✅ **统一体验** - 所有API错误响应格式一致
2. ✅ **易于调试** - 错误码和标识符快速定位问题
3. ✅ **便于维护** - 集中管理，避免冲突
4. ✅ **支持扩展** - 预留空间，易于添加新错误
5. ✅ **国际化就绪** - 支持未来的多语言需求
