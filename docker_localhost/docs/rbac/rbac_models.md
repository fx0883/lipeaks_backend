# RBAC模型设计与使用指南

本文档详细描述RBAC（基于角色的访问控制）系统中的核心数据模型、它们的属性、关系，以及如何在不同场景中使用这些模型。

## 1. 核心数据模型概览

RBAC系统由四个核心数据模型组成：

1. **Permission（权限）**：系统中可执行操作的最小单位
2. **Role（角色）**：权限的集合
3. **UserRole（用户角色关联）**：连接用户与角色
4. **RolePermission（角色权限关联）**：连接角色与权限

## 2. Permission（权限）模型

### 2.1 模型定义

Permission模型是RBAC系统中的基本单元，代表系统中的一个具体操作权限。

### 2.2 属性说明

| 属性名 | 类型 | 是否必须 | 描述 |
|-------|------|---------|------|
| id | 整数 | 是 | 权限的唯一标识符 |
| code | 字符串 | 是 | 权限的代码，如"user:create" |
| name | 字符串 | 是 | 权限的名称，如"创建用户" |
| description | 字符串 | 否 | 权限的描述 |
| category | 字符串 | 是 | 权限的分类，如"用户管理" |
| is_system | 布尔值 | 是 | 是否是系统内置权限 |
| created_at | 日期时间 | 是 | 权限创建时间 |
| updated_at | 日期时间 | 是 | 权限更新时间 |

### 2.3 使用场景

#### 场景1: 权限定义

权限通常在系统初始化阶段定义，按照功能模块和操作类型进行分类。例如：

- 用户模块权限：
  - `user:view`: 查看用户信息
  - `user:create`: 创建用户
  - `user:edit`: 编辑用户
  - `user:delete`: 删除用户

- 文章模块权限：
  - `article:view`: 查看文章
  - `article:create`: 创建文章
  - `article:edit`: 编辑文章
  - `article:delete`: 删除文章

#### 场景2: 权限检查

在业务逻辑执行前，系统需要检查当前用户是否拥有操作所需的权限。

例如：当用户尝试创建新用户时，系统会检查该用户是否拥有`user:create`权限。

#### 场景3: 权限管理

管理员可以通过权限管理界面查看、创建、编辑和删除系统中的权限。非系统权限（is_system=False）可以由管理员自定义，而系统权限（is_system=True）通常不允许修改或删除。

## 3. Role（角色）模型

### 3.1 模型定义

Role模型代表一组权限的集合，是权限分配的主要单位。

### 3.2 属性说明

| 属性名 | 类型 | 是否必须 | 描述 |
|-------|------|---------|------|
| id | 整数 | 是 | 角色的唯一标识符 |
| code | 字符串 | 是 | 角色的代码，如"admin" |
| name | 字符串 | 是 | 角色的名称，如"管理员" |
| description | 字符串 | 否 | 角色的描述 |
| tenant_id | 整数 | 否 | 所属租户ID，NULL表示系统角色 |
| is_system | 布尔值 | 是 | 是否是系统内置角色 |
| created_at | 日期时间 | 是 | 角色创建时间 |
| updated_at | 日期时间 | 是 | 角色更新时间 |

### 3.3 使用场景

#### 场景1: 角色定义

系统预设的角色通常包括：

- `super_admin`: 超级管理员，拥有所有权限
- `tenant_admin`: 租户管理员，拥有租户内大部分权限
- `user_manager`: 用户管理员，拥有用户管理相关权限
- `content_editor`: 内容编辑，拥有内容管理相关权限
- `normal_user`: 普通用户，拥有基本操作权限

#### 场景2: 租户特定角色

对于多租户系统，每个租户可以有自己特定的角色：

- 租户A的"部门经理"角色
- 租户B的"区域主管"角色

这些角色的tenant_id字段会设置为对应的租户ID。

#### 场景3: 角色权限分配

管理员可以为角色分配权限，如：

- 为"内容编辑"角色分配文章管理相关权限
- 为"用户管理员"角色分配用户管理相关权限

## 4. RolePermission（角色权限关联）模型

### 4.1 模型定义

RolePermission是角色和权限之间的关联表，定义了哪些权限属于哪些角色。

### 4.2 属性说明

| 属性名 | 类型 | 是否必须 | 描述 |
|-------|------|---------|------|
| id | 整数 | 是 | 关联记录的唯一标识符 |
| role_id | 整数 | 是 | 角色ID |
| permission_id | 整数 | 是 | 权限ID |
| created_at | 日期时间 | 是 | 关联创建时间 |

### 4.3 使用场景

#### 场景1: 角色权限分配

当管理员为角色分配权限时，系统会创建RolePermission记录：

- 为"内容编辑"角色分配"文章创建"权限
- 为"用户管理员"角色分配"用户查看"和"用户创建"权限

#### 场景2: 权限检查

当系统检查用户是否有特定权限时，会通过用户的角色查找关联的权限：

1. 通过UserRole找到用户拥有的所有角色
2. 通过RolePermission找到这些角色拥有的所有权限
3. 检查所需权限是否在这些权限中

#### 场景3: 角色权限管理

管理员可以在角色管理界面中对角色的权限进行添加或移除：

- 添加权限：创建新的RolePermission记录
- 移除权限：删除对应的RolePermission记录

## 5. UserRole（用户角色关联）模型

### 5.1 模型定义

UserRole是用户和角色之间的关联表，定义了哪些用户拥有哪些角色。该模型特别设计为支持两种用户类型：User和Member。

### 5.2 属性说明

| 属性名 | 类型 | 是否必须 | 描述 |
|-------|------|---------|------|
| id | 整数 | 是 | 关联记录的唯一标识符 |
| user_type | 字符串 | 是 | 用户类型，"user"或"member" |
| user_id | 整数 | 是 | 用户ID |
| role_id | 整数 | 是 | 角色ID |
| is_active | 布尔值 | 是 | 是否激活，可临时禁用角色 |
| start_date | 日期 | 否 | 角色生效开始日期 |
| end_date | 日期 | 否 | 角色生效结束日期 |
| created_at | 日期时间 | 是 | 关联创建时间 |
| updated_at | 日期时间 | 是 | 关联更新时间 |

### 5.3 使用场景

#### 场景1: 为用户分配角色

在用户管理界面，管理员可以为用户分配角色：

- 为User类型的用户ID=1分配"超级管理员"角色
- 为Member类型的用户ID=5分配"内容编辑"角色

#### 场景2: 临时角色分配

通过start_date和end_date字段，可以为用户分配临时角色：

- 为用户分配从2023-01-01到2023-12-31期间有效的"项目经理"角色
- 为临时工分配有限时间的访问权限

#### 场景3: 禁用用户角色

通过is_active字段，可以临时禁用用户的角色而不删除关联：

- 当用户休假时，临时禁用其"部门经理"角色
- 当用户角色需要审核时，初始设置is_active=False

#### 场景4: 角色继承与层次结构

虽然RBAC模型本身不直接支持角色继承，但可以通过为用户分配多个角色来实现类似效果：

- 为团队负责人同时分配"开发者"和"审核者"角色
- 为系统管理员分配多个功能模块的管理角色

## 6. 模型间的关系与交互

### 6.1 User/Member与UserRole的关系

- 一个用户（User或Member）可以拥有多个UserRole关联
- 通过user_type和user_id字段区分不同类型的用户

### 6.2 Role与UserRole的关系

- 一个角色可以被分配给多个用户
- 通过role_id字段关联到Role模型

### 6.3 Role与RolePermission的关系

- 一个角色可以拥有多个RolePermission关联
- 通过这些关联定义角色拥有的权限集合

### 6.4 Permission与RolePermission的关系

- 一个权限可以被分配给多个角色
- 通过permission_id字段关联到Permission模型

### 6.5 用户权限解析流程

当需要检查用户是否拥有特定权限时，系统会按以下流程解析：

1. 查询用户的所有活跃角色（UserRole记录，筛选is_active=True且在有效期内）
2. 查询这些角色拥有的所有权限（通过RolePermission关联）
3. 检查目标权限是否在这些权限集合中
4. 对于特殊用户（如超级管理员），可能会跳过权限检查直接授权

## 7. 多租户环境中的模型使用

### 7.1 租户角色隔离

在多租户系统中，角色可以分为两类：

- **系统角色**：tenant_id为NULL，对所有租户可见
- **租户角色**：特定tenant_id，只对该租户可见

### 7.2 租户数据过滤

当访问角色和权限数据时，系统会根据当前用户的租户上下文进行过滤：

- 租户管理员只能看到和管理自己租户的角色
- 超级管理员可以看到所有租户的角色

### 7.3 跨租户操作

某些特殊场景可能需要跨租户操作：

- 系统管理员向多个租户添加新的系统角色
- 监控多个租户的权限使用情况

## 8. 数据初始化与管理

### 8.1 系统权限初始化

系统初始时，需要创建基础权限记录，通常包括：

- 用户管理权限集：user:view, user:create, user:edit, user:delete
- 角色管理权限集：role:view, role:create, role:edit, role:delete
- 权限管理权限集：permission:view, permission:assign
- 租户管理权限集：tenant:view, tenant:create, tenant:edit, tenant:delete

### 8.2 系统角色初始化

系统预置的角色通常包括：

- 超级管理员（拥有所有权限）
- 租户管理员（拥有租户内大部分权限）
- 普通用户（拥有基本权限）

### 8.3 角色权限关联初始化

为预置角色分配相应的权限：

- 超级管理员：所有系统权限
- 租户管理员：租户内资源管理权限
- 普通用户：基本查看和个人资源管理权限

### 8.4 管理接口

系统应提供以下管理接口：

- 权限管理：浏览、查找、分类系统权限
- 角色管理：创建、编辑、删除角色，分配权限
- 用户角色管理：为用户分配或移除角色，设置角色有效期

## 9. 权限缓存策略

为提高系统性能，权限检查结果通常会被缓存：

### 9.1 用户权限缓存

- 缓存键：user_type + user_id
- 缓存值：用户拥有的所有权限代码集合
- 过期策略：设定合适的过期时间或基于事件触发失效

### 9.2 缓存刷新触发点

以下操作应触发相关用户的权限缓存刷新：

- 用户角色变更（分配新角色或移除角色）
- 角色权限变更（为角色添加或移除权限）
- 用户相关属性变更（如租户变更）

## 10. 使用最佳实践

### 10.1 权限命名约定

采用一致的权限命名约定，提高可读性和维护性：

- 格式：`资源:操作`
- 示例：`user:create`, `article:publish`, `report:export`

### 10.2 角色设计原则

遵循以下原则设计角色：

- **最小权限原则**：角色只包含必要的权限
- **职责分离**：基于职责划分角色，避免权限过度集中
- **易于理解**：角色名称和描述应当清晰明了
- **可扩展性**：允许创建新角色以适应组织变化

### 10.3 权限检查优化

优化权限检查逻辑，提高性能：

- 批量检查权限，避免频繁查询
- 利用缓存减少数据库查询
- 对特殊用户（如超级管理员）使用快速路径

### 10.4 审计与监控

实施权限使用的审计和监控：

- 记录权限变更历史
- 记录重要权限的使用情况
- 定期审查角色权限分配的合理性

## 11. 常见问题及解决方案

### 11.1 权限过度集中

**问题**：某些角色拥有过多权限，违反最小权限原则。

**解决方案**：
- 将大角色拆分为多个职责明确的小角色
- 为用户分配多个角色而非创建包含所有权限的单一角色
- 定期审查角色权限，移除不必要的权限

### 11.2 权限不足

**问题**：用户无法执行某些应有权限的操作。

**解决方案**：
- 检查用户角色分配是否正确
- 检查角色权限设置是否完整
- 检查权限缓存是否过期或失效
- 检查权限检查逻辑是否正确

### 11.3 权限蔓延

**问题**：系统中权限数量不断增长，变得难以管理。

**解决方案**：
- 定期审查和整合类似权限
- 采用层次化权限模型，使用通配符权限
- 基于资源和操作的标准化权限命名约定

### 11.4 多租户权限隔离问题

**问题**：租户间权限数据混乱。

**解决方案**：
- 确保角色创建时正确设置tenant_id
- 在权限检查时加入租户过滤条件
- 实施严格的租户数据访问控制
